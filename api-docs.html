1. Авторизація

Всі запити (крім /api/auth/* та /api/dictionaries/*) потребують JWT токен в заголовку:

Authorization: Bearer <token>
POST /auth/login

Вхід в систему. Повертає JWT токен та дані користувача.

Body:

{
  "email": "master@pestcontrol.ua",
  "password": "admin123"
}

Response 200:

{
  "accessToken": "eyJhbGciOiJIUzI1NiIs...",
  "user": {
    "id": "uuid",
    "email": "master@pestcontrol.ua",
    "fullName": "Іван Майстер",
    "role": "master"
  }
}

Ролі: admin, auditor, master, client

POST /auth/register

Реєстрація нового користувача.

{
  "email": "new@example.com",
  "password": "password123",
  "fullName": "Нове Ім'я",
  "role": "master"
}
GET /auth/me

Поточний авторизований користувач. Для перевірки валідності токена.

Тестові акаунти (пароль: admin123):
Admin: admin@pestcontrol.ua | Auditor: auditor@pestcontrol.ua | Master: master@pestcontrol.ua | Client: client@metro.ua

2. QR-сканування

QR-код на моніторинговій точці містить tagId (наприклад QR-M001-005). Мобільний додаток сканує код і отримує дані точки.

GET /points?tagId={tagId}

Пошук точки за QR-кодом (Tag ID). Повертає масив — зазвичай один елемент.

Приклад: GET /api/points?tagId=QR-M001-005

Response 200:

[
  {
    "id": "uuid",
    "objectId": "uuid",
    "number": 5,
    "tagId": "QR-M001-005",
    "type": "trap",
    "zone": "Склад продуктів",
    "floor": "1",
    "positionX": 0.2,
    "positionY": 0.4,
    "status": "active",
    "qrStatus": "bound",
    "checkIntervalHours": 168,
    "nextCheckDue": "2026-04-28T10:00:00.000Z",
    "lastCheckedAt": "2026-04-21T10:00:00.000Z",
    "notes": ""
  }
]

Якщо точку не знайдено — порожній масив []

PUT /points/{id}/bind-qr

Прив'язати QR-код до точки (змінює qrStatus на bound).

{
  "tagId": "QR-NEW-001"
}
PUT /points/{id}/deactivate

Деактивувати точку і QR-код. qrStatus → deactivated, status → inactive.

3. Моніторингові точки

GET /points

Всі точки. Фільтр: ?objectId={id}

GET /points/overdue

Прострочені точки (де nextCheckDue < now). Для push-повідомлень в мобільному.

Response: масив точок відсортованих по nextCheckDue ASC

GET /points/{id}

Деталі однієї точки.

4. Перевірки точок

Основний робочий процес майстра — створення перевірок після сканування QR-коду.

POST /checks

Створити перевірку. Автоматично оновлює статус точки та створює повідомлення при високій активності або пошкодженому обладнанні.

{
  "visitId": "uuid",
  "pointId": "uuid",
  "objectId": "uuid",
  "activity": true,
  "activityLevel": 3,
  "consumptionPercent": 45,
  "consumptionGrams": 22,
  "pestType": "rodents",
  "equipmentStatus": "ok",
  "correctiveAction": "Замінено приманку",
  "notes": "Сліди гризунів біля стіни",
  "result": "high_activity",
  "remainingGrams": 28,
  "refilledGrams": 50,
  "checkedAt": "2026-04-26T09:30:00.000Z",
  "checkedBy": "uuid-майстра"
}
ПолеТипОпис
activitybooleanЧи виявлена активність
activityLevelnumber (0-5)Рівень активності (0 = немає, 5 = критичний)
consumptionPercentnumber | null% поїдання приманки (для bait_station)
consumptionGramsnumber | nullГрами спожитої приманки
pestTypestringrodents | cockroaches | ants | flies | bed_bugs | mosquitoes
equipmentStatusstringok | damaged | missing | needs_replacement
resultstringclean | low_activity | high_activity | critical
remainingGramsnumber | nullЗалишок приманки (грами)
refilledGramsnumber | nullСкільки додано (грами)
Автоматичні дії після створення:
  • Оновлюється point.lastCheckedAt та point.nextCheckDue
  • Статус точки: triggered (activityLevel ≥ 3), maintenance (damaged/missing), active (ok)
  • Якщо activityLevel ≥ 3 → авто-повідомлення high_activity
  • Якщо equipmentStatus = damaged/missing → авто-повідомлення equipment_issue
GET /checks

Всі перевірки. Фільтри: ?visitId={id}, ?pointId={id}, ?objectId={id}

GET /checks/heatmap/{objectId}

Дані теплової карти для об'єкта. Параметри: ?from=&to=&pestType=&zone=

[
  {
    "pointId": "uuid",
    "x": 0.2, "y": 0.4,
    "score": 12.5,
    "zone": "Склад",
    "floor": "1",
    "checks": 4
  }
]
GET /checks/consumption/{objectId}

Звіт витрати по точках. Параметр: ?months=6

13. Flow: QR-сканування та створення перевірки

Основний сценарій для мобільного додатку

  1. Логін: POST /auth/login → зберегти accessToken
  2. Отримати виїзди: GET /visits?assignedTo={userId}&status=planned
  3. Почати виїзд: PUT /visits/{id} з {"status": "in_progress"}
  4. Сканувати QR: отримати tagId з QR-коду
  5. Знайти точку: GET /points?tagId={tagId}
  6. Показати інфо: номер точки, тип, зона, останній результат
  7. Заповнити форму перевірки: активність, поїдання, стан, фото
  8. Зберегти: POST /checks з даними перевірки
  9. Повторити кроки 4-8 для кожної точки
  10. Завершити виїзд: PUT /visits/{id} з {"status": "completed", "completedAt": "...", "pointsChecked": N}

Сценарій: Прив'язка нового QR

  1. Сканувати новий QR → отримати tagId
  2. GET /points?tagId={tagId} → порожній масив (точка не знайдена)
  3. Створити точку: POST /points з tagId
  4. Або прив'язати до існуючої: PUT /points/{id}/bind-qr з {"tagId": "..."}

Сценарій: Перевірка прострочених точок

  1. GET /points/overdue → список прострочених точок
  2. Показати push-повідомлення або badge з кількістю
  3. Натиснути на точку → навігація до об'єкта
Рекомендації для мобільного додатку:
  • Зберігати токен в secure storage
  • Кешувати словники локально (оновлювати раз на день)
  • Підтримувати офлайн-режим — зберігати перевірки локально і синхронізувати при появі з'єднання
  • Використовувати camera API для сканування QR і завантаження фото
  • Перевіряти /notifications/unread кожні 30 секунд для показу badge
